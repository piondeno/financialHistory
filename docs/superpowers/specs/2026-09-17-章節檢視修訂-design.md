## 1. 任務背景與目標

20 章（1837–2026）已依 2026-09-14 設計文件完成撰寫並通過 `tools/verify_chapter.py`（≥24,000 字、9 節齊全）。抽樣檢視（ch01、ch16）發現品質不均：

- 早期章節（如 ch01）敘事流暢、術語多有解釋
- 後段章節（ch16–ch20）資訊密度極高，大量術語（SIV、repo、haircut、level-3 資產、TAF/SDF/PDCF、tri-party repo…）直接拋出未解釋，段落間因果跳躍較多

本任務對 `chapters/` 全 20 章做系統性檢視與修訂，三大品質標準：

1. **通俗易懂**：以零基礎普通讀者為基準（完全沒學過金融）
2. **前因後果詳細**：每個重大事件的觸發條件與傳導鏈條必須完整
3. **專業名詞解釋**：每章內首次出現即解釋（1–2 句講清「是什麼、怎麼運作」，複雜者加生活化類比）

輔助能力：所需相關資料可透過 browser-search 技能查證。

## 3. 整體流程（兩階段 + 使用者閘門）

```
階段一：檢視
  順序：ch16→ch20（5 章）→ ch01→ch15（15 章）
  每批 2 個 subagent 並行，每章產出報告 docs/reviews/chNN-review.md
  主 session 抽檢品質；每 2 批（4 章）向使用者匯報一次
  20 份報告完成 → 使用者審閱、調整優先級

【使用者閘門】使用者逐章核准 / 刪減 / 改判優先級

階段二：修改（使用者確認後才開始）
  同一順序、同樣 2 個 subagent 並行，每章依核准後報告修改
  每章：修改 → verify_chapter.py 通過 → git commit
```

理由：先後段（ch16–ch20 資訊密度最高、術語最密集，抽樣已證實）；兩階段間放使用者閘門，因「改什麼、改到什麼程度」是價值判斷，由使用者拍板。

## 4. 檢視 Rubric（四大軸 + 優先級）

### 軸 1 — 通俗易懂

- **句級**：過長句（>80 字）、嵌套過深、中英夾雜影響理解、縮寫未展開
- **概念級**：複雜機制有沒有類比或「先講 X 是什麼」的鋪陳
- **段級**：段與段之間有沒有「跳剪」（後段使用了前段未建立的事實）
- **章級**：「歷史背景」是否足以讓零基礎讀者進入（原 spec 要求假設讀者對該年代無先備知識）

### 軸 2 — 因果鏈（前因後果）

- 每個重大事件：前因（觸發條件、誰做了什麼決定、為什麼）是否在事件發生**前**講清楚
- 後果傳導：有沒有明確鏈條（A→B→C，誰被波及、順序、代價落在誰身上）
- 標記「結論先於論證」或「跳過中間環節直接給結果」之處

### 軸 3 — 專業名詞

- 建立該章完整術語清單（中英），逐項記錄：首次出現行號、目前狀態（已解釋／部分／未解釋）
- 判定基準：**以該章內首次出現為準**——每章獨立可讀（符合原 spec 自足設計），章內首現必須讓讀者明白「它是什麼」；已解釋過的同章再出現不需重複
- 「部分解釋」= 只給英文對照或一句含糊帶過，沒有講清運作方式

### 軸 4 — 事實查核（順手查）

- 只針對：存疑日期/數字、前後自相矛盾、與通識明顯不符者
- subagent 標記「待查證」＋建議搜尋式；由主 session 用 browser-search 批次查證後回填報告
- 不逐項重驗所有數據（前期已研究＋自審過）
- 查無結果者依原 spec §8 降級處理原則標註「說法不一」，不得編造

### 優先級定義

| 級別 | 定義 |
|------|------|
| **P0** | 擋住閱讀——零基礎讀者會卡死、因果嚴重誤導、關鍵事實錯誤 |
| **P1** | 傷體驗——術語未解釋但可猜、因果鏈斷但可推、句子過長 |
| **P2** | 打磨——可加類比、可更順 |

## 5. 報告格式（`docs/reviews/chNN-review.md`）

```markdown
# chNN 檢視報告：章節標題
- 日期 / 總評：通俗 __/6　因果 __/6　術語 __/6（A–F 對應 6–1）
- 統計：P0 ×n｜P1 ×n｜P2 ×n｜術語共 m 項（未充分解釋 k 項）

## 1. 術語清單
| # | 術語 | 首現行號 | 狀態(已/部分/未) | 建議處理 | 優先級 |

## 2. 通俗化問題
| # | 行號 | 類型(長句/無鋪陳/跳剪/中英夾雜/其他) | 原文摘錄 | 建議處理 | 優先級 |

## 3. 因果鏈缺口
| # | 行號 | 斷點 | 缺什麼環節 | 建議補寫方向 | 優先級 |

## 4. 事實查核
| # | 行號 | 原文 | 狀態(已查/待查證) | 結論與來源 |

## 5. 總評
2–3 句：本章最大問題、修改後預期改善最大的地方
```

- 行號一律用**修改前行號**，修改階段對照使用
- 表格化以便使用者審閱時快速掃描、逐項打勾/刪減

## 6. 執行機制

### 派工

- 每批 2 個 subagent 並行（`task` 工具單則訊息發 2 個），各讀 1 章全文＋本 rubric，回傳完整報告 markdown
- 順序：ch16/ch17 → ch18/ch19 → ch20（單飛）→ ch01/ch02 → ch03/ch04 → ch05/ch06 → ch07/ch08 → ch09/ch10 → ch11/ch12 → ch13/ch14 → ch15（單飛），共 11 批
- 主 session 收到回傳後寫入 `docs/reviews/chNN-review.md`
- 硬上限：同一時間最多 2 個 subagent（使用者指定）

### 品質閘門（抽檢）

- 每份報告抽 3–5 個 P0/P1 項，對照原文行號核實：問題是否屬實、行號是否正確
- 不合格（捏造問題、行號錯誤、漏掉明顯術語）→ 該章重派一次；第二次仍不合格 → 主 session 自己接手該章

### 事實查核回填

- subagent 標「待查證」項目，由主 session 載入 browser-search 技能批次搜尋，結論回填報告 §4
- 查無結果：標註「說法不一」

### 上下文管理

- 每批完成後壓縮主 session 對話（報告全文已落檔，主 session 只保留批次摘要）
- 每 2 批（4 章）向使用者匯報一次進度統計

## 7. 修改階段規則（階段二）

### 派工

與階段一同構：每章 1 個 subagent、2 個並行、同順序（ch16→ch20、ch01→ch15）。每個 subagent 收到：該章核准後報告＋原文檔，依 P0→P1→P2 順序修改（P2 時間不足可留）。

### 修改原則

- 只改報告核准的項目，不順手重寫未點名段落
- 補術語解釋：1–2 句講清「是什麼、怎麼運作」，複雜者加生活化類比；不寫成百科條目
- 補因果鏈：把缺失環節寫成敘事段落，資料不足時用 browser-search 補查（標註來源）
- 修長句：拆句、降嵌套，保留原有數據與來源標註
- **硬約束**：改完 `verify_chapter.py` 必須通過（≥24,000 字、9 節齊全、年份鏈）；來源隨文標註不得刪減

### 品質閘門

主 session 每章核 verify 輸出＋抽 3–5 個修改點對照報告核實，通過才 commit。
